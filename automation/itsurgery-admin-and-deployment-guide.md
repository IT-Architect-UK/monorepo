# IT Surgery platform — admin & deployment guide

The single reference for how the IT Surgery business system is built, deployed,
monitored, backed up and recovered. Source of truth is this file in the
monorepo (`automation/itsurgery-admin-and-deployment-guide.md`); the Guide tab
on the dashboard renders whatever was last deployed. If they disagree, GitHub
is right and a deploy is owed.

---

## 1. What this system is

A booking-to-cash pipeline for a one-person IT support business, plus the
operations pages to run it. A customer books and pays a £5 fee; the system
creates the CRM records, raises the invoice, handles reschedules and
cancellations (including automatic Stripe refunds under the 24-hour rule),
supports the remote-help session, and asks for the review afterwards.

| Component | What | Where |
|---|---|---|
| Website | Eleventy static site, Netlify | itsurgery.me |
| Bookings | Cal.com (cloud, free tier) | cal.com/it-surgery |
| Automation | n8n 2.x, Docker | n8n.itsurgery.me |
| CRM | EspoCRM, Docker | crm.itsurgery.me |
| Remote help | MeshCentral, Docker | help.itsurgery.me |
| Admin pages | Dashboard · Monitoring · Webmin · Backup · Guide | dashboard.itsurgery.me |
| Server admin | Webmin (also standalone break-glass) | webmin-crm-vps1.itsurgery.me |
| Accounts | Xero (SaaS) | — |
| Payments | Stripe (SaaS) | — |
| Email/calendar | Microsoft 365, via Graph | help@itsurgery.me |

Everything self-hosted runs on **one OVHcloud VPS** (`vps-ad6e2a37`, Ubuntu
24.04): Docker services bound to loopback, nginx in front terminating TLS with
Let's Encrypt. Legal entity behind it all: IT Solution Architecture Limited.

## 2. Networking

**DNS** is in AWS Route 53. `itsurgery.me` (and `www`) point at Netlify;
`crm`, `n8n`, `dashboard`, `help` and `webmin-crm-vps1` are A records to the
VPS. DNS must resolve **before** any playbook that requests a certificate —
certbot proves ownership over plain HTTP.

**Public ports** on the VPS: 22 (SSH, allowed source IPs only), 80 (ACME
challenges + redirect), 443. Everything else is dropped — iptables
default-DROP on INPUT, both IPv4 and IPv6, managed by the espocrm role's
firewall tasks. The ACCEPT rules are inserted before the DROP policy is set;
reversing that order severs the SSH session applying it.

**Loopback services** (never public): n8n :5678, MeshCentral :4430,
Webmin :10000 (its own TLS), oauth2-proxy :4180. Databases (Postgres for n8n,
MariaDB for EspoCRM) live inside Docker networks and expose nothing to the
host. All customer- and API-facing traffic is HTTPS on 443; the remote-help
session runs as websockets over the same port (proxy timeouts are 330s —
longer than MeshCentral's 300s keepalive, or nginx cuts healthy agents).

## 3. Access & authentication

**Admin pages** sit behind **Microsoft sign-in**: oauth2-proxy (Entra ID,
single tenant, app registration `oauth2-proxy — IT Surgery admin`) checked by
nginx `auth_request`. Access is an allow-list of exact addresses — anyone else
authenticates with Microsoft successfully and is then refused. Sign out
bounces through Microsoft's logout and lands on `/signed-out`.

Behind the gate, nginx injects the n8n webhook's basic-auth credential
invisibly. **Webmin keeps its own login on purpose**: miniserv refuses basic
auth in session mode (deliberate upstream hardening), and the workaround
would let a compromised Microsoft account reach root in one click. The Unix
login is the second factor. Do not "fix" this without meeting that argument.

**Break-glass** when Microsoft is down: SSH (key-only, restricted sources),
the OVH KVM console/rescue mode, and `webmin-crm-vps1.itsurgery.me` which
keeps the old htpasswd gate (`/etc/nginx/.htpasswd-webmin`) plus Webmin login.

**Machines can't SSO.** The watchdog reads `/monitoring.json`, basic auth
against `/etc/nginx/.htpasswd-services` — generated by Ansible from the same
vault credential the n8n webhook checks, so that pairing has one password.

**Where credentials live:** human credentials in Bitwarden; deploy-time
secrets in `inventory/group_vars/<group>/vault.yml` (ansible-vault; note the
path — `group_vars/<group>_vault.yml` is silently ignored). The htpasswd files
are created on the box and exist nowhere else.

## 4. Deployment

**Everything deploys from GitHub.** Working rule for the repo: clone fresh to
`/tmp` with a fresh PAT per session — never work on an NTFS mount. On the VPS,
the checkout lives at `/opt/monorepo` and **Ansible runs on the box itself**
against localhost; there is no external controller.

**n8n workflows deploy themselves**: push to `main` triggers the
`Deploy n8n workflows` GitHub Action, which runs `automation/n8n/deploy.py` —
matching by workflow *name*, resolving error-workflow names to ids, activating
everything, then **reading every workflow back and failing the build on any
drift**. A green deploy can be trusted; it was not always so. The repo is the
source of truth — UI edits are overwritten on the next push, and any
credential attached in the UI must be written back into the repo file.

**Everything else needs a playbook** on the VPS:

```
cd /opt/monorepo && git pull && cd automation/ansible
ansible-playbook playbooks/<name>.yml --ask-vault-pass
```

| Playbook | Owns |
|---|---|
| deploy-espocrm.yml | EspoCRM, MariaDB, its nginx vhost, the VPS firewall |
| deploy-n8n.yml | n8n, Postgres, its vhost **and the dashboard vhost** (all admin-page nginx) |
| deploy-meshcentral.yml | MeshCentral and its vhost |
| deploy-webmin-vps.yml | Webmin + its proxy config on this VPS |
| deploy-auth.yml | oauth2-proxy container and config |
| deploy-vitals.yml | The host snapshot script and its one-minute timer |
| server-baseline.yml / others | General estate; not specific to this VPS |

Changed a page/workflow → push is enough. Changed nginx, vitals, Webmin or
auth → the matching playbook. TLS is two-pass everywhere: HTTP-only vhost
first so certbot can answer the challenge, then the TLS block appears.

## 5. Monitoring & alerting

Four moving parts, one set of rules:

- **vitals** — `/usr/local/bin/vps-vitals.sh` writes `/opt/vitals/vitals.json`
  **every minute** (cheap half: memory, disks, containers, systemd units) with
  certificates, backup ages and apt counts **cached 15 minutes** (measured:
  1216 ms cold, 32 ms warm). nginx serves it only to loopback and the Docker
  bridge. The snapshot publishes its own age; the page calls it amber past 5
  minutes, red past 15 — a stale snapshot full of green numbers is the most
  dangerous display this system can produce.
- **The monitoring page** builds its verdict fresh on every load: services by
  asking them (a 401 from Stripe/Xero counts as up — an API refusing an
  unauthenticated request is working), the host from vitals, the last deploy
  from GitHub. Every check node continues past hard failures — otherwise one
  unreachable service would blank the whole page exactly when it matters.
  **Red "no answer"** = couldn't reach it. **Grey** = the check didn't run,
  and it is named in a banner, never counted as fine.
- **The watchdog** polls `/monitoring.json` every 5 minutes and emails **only
  transitions** — gone wrong, or recovered. It has no rules of its own: the
  page's verdict is the only verdict, so they can never disagree. Its state
  dies on redeploy; the first run after one re-learns silently.
- **The error workflow** (`n8n error alert`) emails when any workflow fails
  mid-run. It must be *published* — on n8n 2.x an unpublished error workflow
  silently never fires, whatever older docs say.

Thresholds are printed on the monitoring page itself. Colour grammar
everywhere: green fine, amber this week, red now, grey blind.

## 6. Backup & recovery

Three layers; the Backup tab reports their live truth.

**Layer 1 — nightly application dumps** (live): consistent exports into
`/opt/<service>/backups` — espocrm 02:30 (MariaDB dump; raw DB files copied
live would be corrupt), n8n 02:45 (Postgres dump + data dir), meshcentral
03:15 (**stops the container briefly**; its file DB half-captured restores no
better than none). Same disk as the services: a staging area, not a disaster
copy.

**Layer 2 — OVH automated backup** (verified 2026-08-28): whole-VPS snapshot
daily 08:35 UTC, restored from the OVH panel. 08:35 is after the dumps, so
each snapshot carries that night's exports. **Standard tier keeps exactly one
restore point** — corruption noticed a day late is in the only backup.

**Layer 3 — Proxmox Backup Server** (pending): dumps pushed encrypted via
`proxmox-backup-client` over a private tunnel to PBS in the garage-office
estate — history depth, per-file restore, scheduled verify. Until that server
answers, this layer protects nothing and the tab says so.

### Recovery

*Single service data loss* — stop the service's compose project, restore from
the newest archive in `/opt/<service>/backups` (each backup script's header
documents its own format; the scripts are the executable truth), start, then
check the monitoring page and the service itself. **These steps are untested
until a restore drill has been run — do one before trusting them at 2am.**

*Whole VPS lost* — restore the OVH backup from their panel; the machine
returns as it was at 08:35 UTC, certificates and all. Check the monitoring
page and every container. Booking data since 08:35 exists in Cal.com/Stripe/
Xero and can be reconciled by hand.

*OVH gone too* (fire, account) — until PBS is live this is the uncovered
case. Rebuild path: new VPS → repoint Route 53 A records → playbooks in order
(espocrm → n8n → meshcentral → webmin-vps → auth → vitals) → restore data
from PBS. **MeshCentral's keys are the critical cargo**: restored without
them, every agent on every customer machine is orphaned and must be
reinstalled by hand. The n8n encryption key (vault) is equally unforgiving —
without it, stored credentials are unrecoverable.

## 7. Routine care & rotation

Certificates renew themselves (`certbot.timer` — watched by vitals precisely
because a stopped renewal timer is how certs expire quietly). OS security
updates apply via unattended-upgrades; the rest surface on the monitoring
page — apply promptly, reboot when `/var/run/reboot-required` appears,
preferably against an empty diary.

| Secret | Lives in | Expiry / note |
|---|---|---|
| Entra secret — n8n mail app | Bitwarden + n8n credential | ~Aug 2028, renew in Entra |
| Entra secret — oauth2-proxy | Bitwarden + vault | ~Aug 2028, renew in Entra |
| EspoCRM API key | EspoCRM + n8n credential | rotate on suspicion; dashboard panels go empty when wrong |
| Dashboard basic cred | n8n credential + vault + .htpasswd-services | **three copies — change all or the watchdog breaks** |
| GitHub PAT / n8n API key | GitHub Actions secrets | deploys fail loudly when stale |
| Vault password | Bitwarden | unlocks everything above; guard accordingly |

## 8. Decisions worth not re-litigating

Cal.com over MS Bookings (Bookings' update webhook is broken upstream).
Branch on data, not n8n's error output (`continueErrorOutput` doesn't route
here; three real cancellations proved it). Draw the VPS as a container, not a
peer. Webmin keeps its login (§3). OVH Premium backup not bought — PBS does
history better and free. Remote support is Windows-only (MeshCentral has no
Wayland capture; Mac/Linux by arrangement). One n8n per business — hosting it
for clients needs an Embed licence; deploy per-client instead.
